# Как получить EXE и APK из v0.11 и проверить их

## Быстрее всего — тестовая сборка через GitHub Actions

Разместите **исходники** (без рабочих ключей/секретов/конфигураций) в **приватном GitHub-репозитории**, сохранив каталог `.github/workflows/`. Откройте вкладку **Actions → Test and build prototypes → Run workflow** или сделайте push в ветку `main`.

При сборке Windows `npm run build:ui` запускает Vite и проверяет полученный `dist/index.html` на относительные пути JS/CSS для `file://`. Ошибка сборки или отсутствующий ассет остановят выпуск артефакта.

В случае успешного выполнения будут доступны два артефакта запуска:

- `universal-stream-windows-unsigned` — неподписанный EXE-установщик Windows;
- `universal-stream-operator-debug-apk` — отладочный APK, подписанный тестовым ключом Android debug (НЕ релизной подписью).

Пока workflow в реальном GitHub не выполнен, сборки не считаются успешными. CI не устанавливает приложения, не создаёт публичный VPN/VPS и не подтверждает наличие видеокадров.

## Ручная сборка на Windows

- Windows: установите Node.js 22+, Docker Desktop и официальный WireGuard; запустите `cd windows`, `npm install`, `npm run dist:win`. Файл EXE должен появиться в `windows/release/` после успешной сборки.
- Android: установите JDK 17, Android SDK 35 / Android Studio, выполните `powershell -File android/build-apk.ps1`. Скрипт использует Gradle 8.9 или создаёт wrapper; APK должен появиться в `android/app/build/outputs/apk/debug/`.
- Перед установкой убедитесь, что исходники получены из доверенного места, а сторонние драйверы и службы устанавливаются из официальных источников.

## Последовательность реального испытания

1. На Windows запустите Docker, включите VPN и Windows-приложение. Проверьте адрес WireGuard `10.77.0.1` и входящие TCP 3100/7880/7881, UDP 7882 **только из VPN**.
2. Создайте комнату и используйте **«Проверить видео»**. Убедитесь, что движущийся тестовый кадр действительно появился в видеосетке.
3. На одном Android-устройстве с возможностью установки сторонних APK разрешите VPN и MediaProjection. Начните с профиля **360p / 15 FPS**.
4. Проверьте отображение на Windows через тот же Wi-Fi, затем через 4G/5G другой сети. Если виден статус «подключён», но изображения нет, проверьте наличие published screen-share track и порт UDP 7882.
5. Проверьте отзыв ключа во время активного видео и кнопку «Проверить отключения операторов». Отдельно проверьте восстановление после временного отключения LiveKit.
6. Проверьте 2–3 одновременных устройства и измерьте задержку, потери кадров, загрузку CPU и потребление трафика. Только затем увеличивайте число операторов.

## Чего нельзя обещать до испытаний

Не подтверждены совместимость с любым пультом, отсутствие конфликтов с приложением пилотирования, постоянная работа Android-процесса в фоне, прохождение CG-NAT на всех провайдерах, качество соединения и заявленные задержки/масштабирование. Для пультов без Android или с запретом захвата экрана потребуется иной способ захвата изображения.

## Проверка исходного проекта без загрузки зависимостей

Запустите `bash RUN_TESTS.sh` и `node scripts/source-audit.mjs` (или `RUN_TESTS.ps1` на Windows). Это тесты исходного кода, а не запуск настоящего видеосервера.

## v0.11: проверка перед полевым испытанием

Запустите `RUN_TESTS.sh` или `RUN_TESTS.ps1` до сборки. Новые тесты проверяют строгую привязку каждого операторского кода к VPN-адресу, блокировку при отсутствии соответствующей записи, а также фильтрацию секретов в диагностическом JSON. На реальном Windows создайте два операторских ключа, подключите два разных пульта и проверьте, что **каждый код работает только на своём выданном VPN-пире**. После испытания отзыва доступ не должен восстанавливаться от повторного ввода того же кода.
